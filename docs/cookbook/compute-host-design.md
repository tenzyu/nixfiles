# Personal compute platform design

## Contract

NixOS configures the host. Incus manages dynamic instances. T3 Code manages agent sessions and projects. The Incus `lab` project is a shared execution permission boundary, not a T3 project or knowledge partition. No repository name is embedded in it. Do not add a custom scheduler, registry, governor or execution API. Use native systemd/Nix for finite jobs and NixOS tests for reproducible multi-machine evidence; use Incus for interactive or persistent environments.

Incus uses a directory pool on the existing filesystem. It does not require repartitioning, migration, or a new filesystem. Only the operator can access the default project. The restricted `lab` project has a separate NAT bridge and managed volumes. It prohibits arbitrary host disk, GPU, proxy, privileged container, and raw VM attachment. This does not provide network egress isolation from the rest of the host/LAN, per-agent identity, or a security sandbox for an agent already running as an administrator. Both projects share physical CPU, memory, and I/O. The `lab` project limits aggregate CPU, memory, and instance count. VM admission remains disabled until lifecycle tests pass. The configuration sets neither a storage quota nor automatic VM memory overcommit. Before a large experiment, inspect pressure stall information (PSI), available memory, disk space, and OOM logs.

The native preseed declares the pool, bridges, project and default profile. Incus merges these definitions at daemon initialization or restart and does not reconcile them continuously. Do not edit these definitions independently or use the default profile as a per-application configuration. Runtime-created instances and custom profiles remain Incus-owned. A soft Incus daemon restart is intended to preserve running guests. A host reboot stops all guests.

Existing declared services have explicit lifecycle boundaries independent of the old host-coupled release model. Minecraft, T3 Code and SplitCast now have independent native Nix deployment artifacts and generation profiles. Minecraft deliberately keeps its existing nspawn machine, data, Tailnet identity and backup protocol; converting an already independent machine to Incus would introduce an unnecessary data/identity and backup migration. T3 remains a single user control plane so it can operate Incus without exposing the management API outside loopback. SplitCast retains its pinned upstream manual parity gate and host GPU/audio prerequisites; no production service is started by this migration. The Nix daemon/remote builder, Tailscale, SSH, drivers and rootless Docker are host capabilities, not application releases. See [existing workload migration](compute-workload-migration.md) for the concrete activation and rollback gates. No live data is moved by the PR.

## Tailnet-only ingress (host invariant)

No application listener, public port forward, DMZ, physical NIC passthrough or public reverse tunnel may expose services through neko7's uplink. External access is exclusively authenticated Tailnet access (Serve, SSH forwarding, or a separately approved guest Tailnet identity). Never use Funnel or an Internet-facing reverse tunnel. Obtain operator approval before you publish an endpoint. The existing Proxmox/router port-opening prohibition remains unchanged.

The host selects the independent `tailnet-ingress` feature. Its native nftables inet table filters new TCP/UDP input and unsolicited forwarding arriving on the declared NAT uplink (`ens18`), including DNAT to any guest. It leaves loopback, internal interfaces, Tailnet traffic, outgoing connections and their replies unchanged. DHCP client traffic and the existing encrypted Tailscale UDP transport are exceptions to the guard, not new firewall openings; ICMP/control traffic remains governed by the ordinary firewall. The guard is not an outbound filter, and established connections are deliberately preserved. NixOS NAT port forwards and DMZ configuration are rejected at evaluation. Restricted Incus credentials cannot attach a physical NIC, add proxy devices or administer the shared network.

The packet filter blocks direct ingress. It does not protect against host administrators, arbitrary outbound tunnels or changes to Tailnet control-plane policy. Funnel uses outbound connectivity, so nftables cannot reliably distinguish it from legitimate Tailnet traffic. The operator must verify in the Tailnet policy that Funnel capability is not granted to neko7 or guest identities (including broad nodeAttrs selectors), and check `tailscale serve status --json` for any enabled `AllowFunnel` entries on those nodes. Do not modify existing Serve routes or Tailnet policy automatically. Verify other uplinks if hardware/network topology changes.

The separate ingress CI test uses real network namespaces with an allowed host listener, a routed guest and DNAT. It checks that the drop counters increase and that host and internal HTTP and outbound NAT still work. It does not substitute for actual Tailscale connectivity, current Tailnet policy or Proxmox firewall evidence.

See the [compute host operation procedure](compute-host.md).
