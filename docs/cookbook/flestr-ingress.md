# Flestr transport and the host ingress contract

This review uses the user-supplied Flestr main snapshot with archive SHA-256 `ca190f60398d5c9edb5357a16524f99fe38ac983be4c12c9e188a84b4f175595`. The source is not vendored and no SplitCast dependency is introduced. The snapshot's DESIGN.md identifies v0.4.2. This is static source evidence, not a live WAN or cryptographic audit.

- `crates/flestr-core/src/noise.rs:19-24,67-95,104-154,181-227`: Noise IK (25519/ChaChaPoly/BLAKE2s), independently pinned 32-byte peer keys, authenticated initiator static key, bounded pending handshakes, 8192-packet replay window updated only after authentication.
- `crates/flestr-net/src/ice.rs` (`prepare_ice`, `PendingIce::complete_with_timeout`, `IcePath::step`, `bind_candidates`): bind concrete UDP sockets, gather host/STUN candidates, exchange offers, nominate a direct path and retain the selected socket for ICE keepalive and media. Automatic bind enumerates usable interfaces, so explicit candidate selection is appropriate when a particular overlay is required. No TURN/media relay fallback is documented.
- `crates/flestr-net/src/lib.rs:61-141,308-328`: one pinned peer SocketAddr; receive filters the source and demultiplexes ICE vs Noise. This is an authenticated application datagram transport, **not** a routed multi-peer IP overlay, VPN or general-purpose login/authorization mechanism.
- `crates/flestr-net/src/rendezvous.rs` (`Token::parse`, `agent_for`, `exchange`, `serve`): one sender/receiver pairing with shared 256-bit hex bearer token; HTTPS uses WebPKI, redirects disabled, and plain HTTP is supported only for trusted network use. Keep peer keys separately trusted; rendezvous does not replace Noise identity. Use HTTPS for external signaling, or a previously approved private path. Never put bearer tokens/private keys into Git/Nix store.
- `deploy/cloudflare-rendezvous/README.md`: optional Worker exchange, not media relay. Its deployment is a separate external publication decision.

No new physical ingress port is required or authorized. The existing nftables guard denies NEW TCP/UDP arriving on the uplink, preserves outbound and established/related return traffic. An outbound ICE check from each bound socket can establish UDP conntrack and NAT mappings; a later incoming packet matching the reverse tuple can pass. STUN and peer candidate tuples are distinct. A STUN mapping alone does not admit arbitrary peers. Unprimed static receiver mode on the physical interface will fail by design; use the existing Tailnet path or mutually initiated ICE. Symmetric NAT, upstream Proxmox/router filtering, tuple mismatch or conntrack timeout may still prevent direct nomination; do not open an unsolicited listener as fallback. The host firewall filters packets. Noise authenticates peers and sessions. Existing egress can carry arbitrary tunnels. The firewall does not confine egress.

The ingress CI now separately checks unsolicited UDP denial and real outbound UDP replies on the host and from a NATed guest, with no new allowed uplink application port in production. This is a generic Linux conntrack acceptance test, not execution of Flestr or proof of WAN success. Actual Flestr end-to-end ICE, replay, route failure and recovery evidence belongs to the transport/application test suite. Explicit operator approval and positive/negative acceptance are required for another authenticated overlay or a public rendezvous. No new port, tunnel, identity, or SplitCast configuration is activated by this PR.
