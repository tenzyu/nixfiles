# Home migration needs a separate data mover

Research for [ADR-0002, I-3 and PR2k](0002-invariant-safety.md#delivery-order-and-decision-gates). Reviewed 2026-11-19. The source baseline is [main at `0daacae`](https://github.com/tenzyu/nixfiles/commit/0daacae75f19dc2b01712c26471b42b2c6bc9ca3). The four rule owner files are identical in [PR #48](https://github.com/tenzyu/nixfiles/pull/48). This report recommends a decision. It does not authorize an implementation or an apply.

## Recommendation for the parent decision

Keep the local migration adapter and native Home Manager configuration. Keep xdg-ninja as an optional diagnostic where it is already packaged. Do not make it an input to the planner. Reject antidot and boxxy as migration dependencies. Take no upstream code, rule files, or new packages. After 2c and explicit parent approval of this disposition, 2l can harden the local adapter against I-3. If it cannot prove ownership and exclude other writers for a required replacement, it must reject the batch before the first move. Any narrowing that changes a previously successful case needs separate compatibility review.

Changing an app's save path does not move credentials, profiles, history, or caches already on disk. A diagnostic can identify an old path but cannot establish that the move is safe. A launcher can redirect access while leaving old data where it was. Home Manager checks the current generation's link targets, not the layout a legacy move would leave behind.

## Antidot cannot enforce the move and recovery contract

The review started with `Migrate.Apply`, `MovePath`, `Rule.Apply`, and the CLI command list. The pins are [release `v0.6.3`, `2d679d72515f46a824c05360da5b7a6436f5b906`](https://github.com/doron-cohen/antidot/tree/2d679d72515f46a824c05360da5b7a6436f5b906), commit 2022-07-11, [released 2022-07-13](https://github.com/doron-cohen/antidot/releases/tag/v0.6.3), and [observed `master`, `1dd77c7478d70730bdf4f83afd8e8e0e5c39f41b`](https://github.com/doron-cohen/antidot/tree/1dd77c7478d70730bdf4f83afd8e8e0e5c39f41b), commit 2026-05-12. Neither is a nixfiles dependency. The branch has newer rules and changes how `clean` selects them. It has the same move and conflict behavior.

- [`Migrate.Apply`](https://github.com/doron-cohen/antidot/blob/2d679d72515f46a824c05360da5b7a6436f5b906/internal/rules/migrate.go#L17-L47) stats the source, makes destination parents, then calls `MovePath`. [`PathExists` and `MovePath`](https://github.com/doron-cohen/antidot/blob/2d679d72515f46a824c05360da5b7a6436f5b906/internal/utils/files.go#L65-L120) reject a known existing file or nonempty directory, but treat an empty directory or dangling link as absent. The subsequent ordinary rename is not a no-replace operation. It can replace a leaf that passes the check or appears later. The optional link is a separate action after the move. At both pins the `os.Symlink` arguments name the already-moved destination as the link path, so that step can fail after the data has moved. It is not a restoration mechanism.
- [`MoveFile` and `MoveDirectory`](https://github.com/doron-cohen/antidot/blob/2d679d72515f46a824c05360da5b7a6436f5b906/internal/utils/files.go#L25-L63) handle **any** rename failure, not only a cross-filesystem error. The file fallback writes directly to the destination with `os.Create` and removes the source after copying. It neither preserves the source inode nor checks the final close error before removal. The directory fallback delegates to `otiai10/copy` and then removes the source tree. A removal error in that path is a warning, not a failure. Neither path supplies no-replace publication or the required flush sequence. See the [same functions on reviewed `master`](https://github.com/doron-cohen/antidot/blob/1dd77c7478d70730bdf4f83afd8e8e0e5c39f41b/internal/utils/files.go#L30-L125).
- [`clean` on `master`](https://github.com/doron-cohen/antidot/blob/1dd77c7478d70730bdf4f83afd8e8e0e5c39f41b/cmd/clean.go#L42-L78) previews and prompts per rule. [`Rule.Apply`](https://github.com/doron-cohen/antidot/blob/1dd77c7478d70730bdf4f83afd8e8e0e5c39f41b/internal/rules/rule.go#L34-L45) logs an action error and stops that rule without propagating it. Later rules can still run and the CLI can report cleanup finished. The action set includes [deletion](https://github.com/doron-cohen/antidot/blob/1dd77c7478d70730bdf4f83afd8e8e0e5c39f41b/internal/rules/delete.go#L14-L26). Neither pin provides full-batch preflight, journaled conflict backups, intent/completion records, or a restore command. A retry sees the current paths without knowing whether they are the original entries or partial results. The README's backup note is about antidot's shell export and alias files, not moved app data.

The Go build uses Cobra, Survey, YAML, and `otiai10/copy` v1.7.0, among [other pinned modules](https://github.com/doron-cohen/antidot/blob/1dd77c7478d70730bdf4f83afd8e8e0e5c39f41b/go.mod). A pinned binary alone would not pin the rules: [`update` fetches `master/rules.yaml`](https://github.com/doron-cohen/antidot/blob/1dd77c7478d70730bdf4f83afd8e8e0e5c39f41b/cmd/update.go#L13-L24). The [reviewed rules](https://github.com/doron-cohen/antidot/blob/1dd77c7478d70730bdf4f83afd8e8e0e5c39f41b/rules.yaml) give path leads for Cargo, Rustup, GTK 2, Go, and npm's cache. They put Bash and Node history under XDG data, not state. The npm init path is advice in the npm rule, not a move rule for `.npm-init.js`. Even where the paths agree, none of those rules supplies our process, collision, or recovery policy. Extracting just `MovePath` would retain the decisive failure paths.

Both [release LICENSE](https://github.com/doron-cohen/antidot/blob/2d679d72515f46a824c05360da5b7a6436f5b906/LICENSE) and [branch LICENSE](https://github.com/doron-cohen/antidot/blob/1dd77c7478d70730bdf4f83afd8e8e0e5c39f41b/LICENSE) are MIT with the literal placeholder `Copyright (c) [year] [fullname]`. No separate project NOTICE was found. Do not invent an attribution or vendor the files. The release is old, but the later branch activity does not resolve the contract failures.

## The other candidates solve different problems

### xdg-ninja diagnoses old paths

[`packages-common.nix`](../../modules/50-features/bundles/packages-common.nix) already selects xdg-ninja. The [root nixpkgs recipe](https://github.com/NixOS/nixpkgs/blob/f68407657ad294471eb4b2e65d193df26edf729f/pkgs/by-name/xd/xdg-ninja/package.nix) selects [revision `f2ab12bbf1cf60dc3cc9459d122811c55ba88150`](https://github.com/b3nj5m1n/xdg-ninja/tree/f2ab12bbf1cf60dc3cc9459d122811c55ba88150), commit 2026-05-10, package `0-unstable-2026-05-10`. The latest tagged release observed was `v0.2.0.2` from 2024-02-04. The branch had newer activity on 2026-10-04, not part of the pin. The [LICENSE](https://github.com/b3nj5m1n/xdg-ninja/blob/f2ab12bbf1cf60dc3cc9459d122811c55ba88150/LICENSE) is MIT, copyright 2022 b3nj5m1n. No separate project NOTICE was found.

The package wraps a shell script with `jq` and `glow` and ships `programs/*.json`. The [scan and report loop](https://github.com/b3nj5m1n/xdg-ninja/blob/f2ab12bbf1cf60dc3cc9459d122811c55ba88150/xdg-ninja.sh#L200-L256) prints advisory text for known paths and returns the count of fixable findings, or `101` above 100. It does not run the displayed help as a migration, preflight destinations, or recover data. Its [path expansion](https://github.com/b3nj5m1n/xdg-ninja/blob/f2ab12bbf1cf60dc3cc9459d122811c55ba88150/xdg-ninja.sh#L117-L153) uses shell `eval` on rule-derived input, and `XN_PROGRAMS_DIR` can select another rule directory. Treat the rules as trusted diagnostic input, not inert third-party data. The diagnostic's exit status is not `check --require-noop`.

**Partial use: references only, no files extracted.** The matrix cites individual rules at the package pin and calls out disagreements. When the package pin changes, recheck the cited advice against current app source or vendor docs before changing any owner rule. The pinned table is not a generated migration manifest. Do not wire the diagnostic into activation or the runner.

### boxxy redirects only launched processes

The [root nixpkgs recipe](https://github.com/NixOS/nixpkgs/blob/f68407657ad294471eb4b2e65d193df26edf729f/pkgs/by-name/bo/boxxy/package.nix) selects [boxxy `v0.8.5`, `1f94d152d4a24c5fc42a67f4efa3fcb4879d54f2`](https://github.com/queer/boxxy/tree/1f94d152d4a24c5fc42a67f4efa3fcb4879d54f2), commit and [release](https://github.com/queer/boxxy/releases/tag/v0.8.5) from 2024-07-07. The default branch had later activity on 2026-01-18, not reviewed as the package. The [LICENSE](https://github.com/queer/boxxy/blob/1f94d152d4a24c5fc42a67f4efa3fcb4879d54f2/LICENSE) is MIT, copyright 2023-present amy null. No separate project NOTICE was found. The Rust build uses the [Cargo lock](https://github.com/queer/boxxy/blob/1f94d152d4a24c5fc42a67f4efa3fcb4879d54f2/Cargo.lock), `pkg-config`, and Oniguruma. Nixpkgs marks this Linux package broken on AArch64.

The [enclosure](https://github.com/queer/boxxy/blob/1f94d152d4a24c5fc42a67f4efa3fcb4879d54f2/src/enclosure/mod.rs#L74-L111) creates Linux user and mount namespaces. It [ensures paths and bind mounts the rewrite path over the legacy location](https://github.com/queer/boxxy/blob/1f94d152d4a24c5fc42a67f4efa3fcb4879d54f2/src/enclosure/mod.rs#L248-L386) and [runs the child inside that view](https://github.com/queer/boxxy/blob/1f94d152d4a24c5fc42a67f4efa3fcb4879d54f2/src/enclosure/mod.rs#L458-L501). A type mismatch can fail the [mount check](https://github.com/queer/boxxy/blob/1f94d152d4a24c5fc42a67f4efa3fcb4879d54f2/src/enclosure/fs.rs#L59-L106), but an existing same-type legacy entry can be hidden, not migrated or merged. The tool may create host-side placeholders and remove tracked temporary paths on normal exit. That cleanup is not data restoration. The launch path uses process tracing and [loads user and ancestor-directory rule files](https://github.com/queer/boxxy/blob/1f94d152d4a24c5fc42a67f4efa3fcb4879d54f2/src/config/mod.rs#L44-L82). None of this proves that other processes cannot write the old or new path.

**Reject for 2l.** Every caller would need the wrapper to see the same redirected layout. The four owners already have app-specific configuration, with an `adb`-only wrapper where needed. Adding a general wrapper would expand the runtime dependencies and trust boundary without preserving or recovering any existing data. No upstream files are candidates for extraction.

### Home Manager owns generation links, not legacy data

The [flake lock](../../flake.lock) pins [Home Manager `5643e73425b85ac359ba2aaf83deae8ce1cd7968`](https://github.com/nix-community/home-manager/tree/5643e73425b85ac359ba2aaf83deae8ce1cd7968), commit 2026-11-17 on the configured `release-26.05` line. The input follows root nixpkgs. The [LICENSE](https://github.com/nix-community/home-manager/blob/5643e73425b85ac359ba2aaf83deae8ce1cd7968/LICENSE) is MIT, copyright 2017–2026 Home Manager contributors. No separate project NOTICE was found. The link path uses the Nix module DAG and generated Bash helpers with `find`, `cmp`, and coreutils.

[`checkLinkTargets`](https://github.com/nix-community/home-manager/blob/5643e73425b85ac359ba2aaf83deae8ce1cd7968/modules/files.nix#L140-L167) walks file and link entries in the new generation before `writeBoundary`. The [checker](https://github.com/nix-community/home-manager/blob/5643e73425b85ac359ba2aaf83deae8ce1cd7968/modules/files/check-link-targets.sh#L7-L51) recognizes generation links by a store path pattern. It skips forced path prefixes, accepts equal content, and can allow a configured backup for non-links. Its basic existence test is `-e`, not a test that also counts dangling links. It does not reserve the checked leaf. [`linkGeneration`](https://github.com/nix-community/home-manager/blob/5643e73425b85ac359ba2aaf83deae8ce1cd7968/modules/files.nix#L187-L289) runs after `writeBoundary`. It cleans up old generation links and can back up current entries before force-linking the new generation. A backup command's success is assumed by the check, and the link step's error message on backup failure is not a transaction rollback. Generation rollback changes managed links, not moved user data.

**Keep the native integration.** [Our activation module](../../modules/50-features/home/home-migration.nix) supplies enabled `home.file` targets to a separate check before both Home Manager barriers. The local planner checks for managed files that would appear after a legacy move. Native backup and `force` settings do not substitute for that check or for intentional data moves. Keep the existing input and public options. Do not extract the checker or change backup settings for 2l.

All four project licenses require the copyright and permission notices with copies or substantial portions. The report links to upstream files and uses independently written summaries. There are no imported files or new notices to ship. Any future extraction would require a new decision naming the exact files, their notices and dependencies, how to track updates, and isolated contract tests after extraction.

### Evaluated order and activation boundary

The table IDs below name ordered manifest entries, not runtime actions. The planner reads the list in order. It can omit a missing source or add a backup, repair, or rewrite. It models earlier moves when checking later rules. That matters for H3 before H4 and H6 before H7. H3 and H4 use the most specific matching legacy prefix when repairing absolute links. H1 validates the named JSON and TOML files during planning and can revisit them after a completed directory move.

## What 2l still has to prove

[The current adapter](../../assets/home-layout/migrate.py) preflights the batch, accounts for future managed-file collisions, and probes for relevant same-UID processes. The move path journals intent, uses Linux `RENAME_NOREPLACE`, flushes both parents, and journals completion. That preserves the moved inode on a successful rename and avoids fallback copies. However, this is not an atomic batch. A saved target and a later source rename are separate operations. Process probes do not exclude writers, the move uses pathname resolution, and creating new parent and journal entries has its own durability requirements.

Plan and commit `Move`, `RepairSymlink`, and `RewriteReference` separately. The two replacements currently use `os.replace`. An identity recheck is not a conditional replacement at commit time. A synced rewrite stage does not make the reference backup or final directory entry durable. 2l needs evidence for the approved roots and leaf operations, a fixed lock for cooperating writers, and an explicit ownership and writer boundary for replacements. Retain the two cache backup rules and repair semantics unless the parent approves a compatibility change. Require read-only reconciliation of the actual source, target, backup, and journal after interruption or uncertain completion. No journal record by itself proves that an entry survives. Keep reference contents out of diagnostics.

Acceptance after 2c and the parent decision belongs to `INTENT-01`, `BOUNDARY-01`, `LOCK-01`, `PUBLISH-01`, `PUBLISH-02`, `OWNED-01`, and `RECOVERY-01` where applicable. In particular, test interruption around move intent, rename, backup flush, publication, parent flush, and completion against the packaged runner. Prove that an unsupported replacement blocks the entire batch before moving data. None of the reviewed upstream paths closes that gap. No further tool comparison is needed unless a candidate can meet the same writer, no-replace, and recovery requirements with less local code.
