11/08 実装コスト解析：測定前に確定できること

この画面は11/07の正本測定と、osu!framework・BASS・PipeWire・Linuxカーネル実装から導いた費用モデルを結合する。旧ドキュメントの「実機測定が必要」は全項目共通の前提ではない。ソースコードで確定／計算で確定／実機でしか確定しないを分離した。

Audio：サンプルのPlay()は発音ではない

Keyboard Handler → InputManager.GetPendingInputs() → Update/judgement → SampleChannelBass.Play() → AudioComponent.EnqueueAction(new Task(action)) → Audio Thread: AudioComponent.Update() → Task.RunSynchronously() → bassMixer.ChannelPlay() → Native BASS mixer (sample onset quantization) → ALSA-compatible output → PipeWire data-loop → ALSA PCM → snd_hda_intel → ALC257 DAC

SampleBassFactoryは事前にBass.SampleLoad()したサンプルからBass.SampleGetChannel()でチャンネルを取得する。毎回ファイルをデコードする前提で重さを推定しない。AudioComponentのTaskはAudio Threadで同期実行され、各ヒットごとに.NET ThreadPoolを新設するわけではない。一方でTaskオブジェクトとキューは存在する。BASSのDevicePeriod（サンプルなら負数指定）は、PipeWire graph quantumとは独立する。SampleChannelBass.cs、AudioComponent.cs、sample onset Issue #6650。

PipeWire：周期を半分にしてもサンプル計算量は倍にならない

量子サイズ (48kHz)周期graph cycle/s結論
512 frames10.667 ms93.75固定処理回数は少ない
256 frames5.333 ms187.5最新観測の自動選択値
128 frames2.667 ms375256との差187.5 cycles/s
64 frames1.333 ms750256との差562.5 cycles/s
T = Q / Fs; graphの費用 ≈ sample_count × per_sample_cost + graph_cycles × per_cycle_cost。
256→128の場合、仮に固定費0.1ms/cycleならCPU増分18.75ms/s＝1.875%（論理CPU 1個の時間）。固定費0.02msなら0.375%。数値は仮想単価に対する感度解析でありneko5の実測値ではない。

当日の観測では、force-quantum=0でもPipeWire driverは256 frames。したがって0と256を比較するだけでは、実際の出力周期が異なるという前提が成立しない。また、ALSA period 1024/48000とBASS periodは独立している。pw-topの各値の仕様、PipeWire runtime quantum。

Input / Update / Draw：ドライバを消しても上限は伸びない

層コードで確定する費用先に否定・採用できる方針
USB/HIDO3C 1ms、CTL-472 2ms endpoint descriptor。イベント処理の配信が別途存在OS側の1000Hz poll設定では2msのタブレット報告を生成できない。内蔵OTDを維持
Input→UpdateKeyboardHandlerとOTD HandlerはConcurrent Queueへ投入。InputManager.Updateが取り込み、Update tickが時刻のゲート入力関係をすべて1ms遅延と足し合わせない。直接HID入力への変更は集中/座標変換契約を再実装するリスクがある
UpdateScheduler.Update→OnNewFrame→Root.UpdateSubTree→GenerateDrawNodeSubtree、GC・シーン負荷通常の上限1000Hzは実装が意図した上限。安易な上限解除はGC・GPU発行コスト増
DrawTripleBuffer、GL描画・GPU送信・SDL GL swap。GL + VSync時はWaitUntilIdleでglFinish相当VSync同期点は明示的なコスト。Direct Scanoutはosu!前面で成立済みと維持する

一次ソース：GameHost、ThrottledFrameClock、evdev.c。

SplitCast：メモリ流量と同期経路から先に判定する

1280×720×4B×60fps = 221.184 MB/s（RGBA8 raw）。1366×768なら251.781 MB/s。NV12（1366×768）は94.418 MB/s。仮にH.264を12 Mbit/sとすれば約1.5 MB/sで、720p rawはその約147倍（いずれも payload）。

目標経路：KMS plane→権限分離broker→DMA-BUF→GPU/VAAPIでRGB→NV12→hardware H264→圧縮ネットワーク転送→neko7 OBS/NVENC。CPU readback + reuploadは大量転送に加えDMA同期点を増やし得るため、ドライバに入る前に設計候補から下げられる。GSR/KMSはDirect Scanoutと両立できてもGPU帯域・熱費用はゼロではない。画面取得はゲームプロセスにフックせず、最新フレーム優先の有界キューで遠隔側の遅延を切る。FFmpeg kmsgrab、DRM ioctl、DMA-BUF fences。

次に進むための結論

AudioのBASSネイティブperiodとサンプル開始量子化、Updateのper-frame work/allocations、DrawのGPU同期点、SplitCastのCPU readback・待機・バッファ寿命を実装から最優先で扱う。計測はコードで決められない最後の数値にのみ用い、探索の代替にしない。恒久設定の追加は現時点では行っていない。
