## 3. Inputを、入力イベントがゲームへ到達する時刻まで追う

O3Cの経路は `switch → firmware scan/debounce → USB interrupt IN report → xHCI → usbhid → input core → evdev → libinput → Hyprland → Wayland keyboard → SDL3 → KeyboardHandler → PendingInputs → InputManager.Update → OsuInputManager → judgement` である。ペンは `digitizer → USB report → kernel HID/hidraw等 → osu!プロセス内のOpenTabletDriver → OpenTabletDriverHandler → PendingInputs → InputManager.Update` で合流する。実機CTL-472ではevent5とhidraw5/6のノードが確認され、1-4.2経由で同じxHCIコントローラーに接続している。O3Cは別のUSB 1-2であり、どちらもUSB runtime PMは`on`。今回のCTL-472のInterrupt IN端点は2ms設定であり、「USB端点から1000Hzが保証される」という仮説は採用できない。ペンのカーネル側インターフェースは実際のドライバにより異なるため、すべてのペンがhidrawを経るとは断定しない。

Linuxの `drivers/hid/usbhid/hid-core.c` にある `hid_irq_in()` はURB完了を受け、正常時に `hid_safe_input_report()` を呼び、URBを再投入する。`-EPIPE`等ならhalt解除・リセット処理へ移る。これが散発的なUSB停止を調べる起点になる。`drivers/input/evdev.c` は `evdev_pass_values()` でタイムスタンプを埋め、`SYN_REPORT`でユーザー空間をwakeする。バッファあふれでは `SYN_DROPPED` を通知する。デバイス内の物理的なスキャン時刻とevdevタイムスタンプは同じとは限らない。

osu!framework側では `SDL3Window.Input.cs::handleKeyboardEvent()` が `KeyDown` / `KeyUp`を呼び、`KeyboardHandler`が `new KeyboardKeyInput(key, true/false)` を `ConcurrentQueue<IInput>` に追加する。確認したコードではSDLイベントのタイムスタンプを `KeyboardKeyInput` のコンストラクタへ渡していない。ペンも `OpenTabletDriverHandler::enqueueInput()` でキューへ渡す。`InputManager.GetPendingInputs()` がHandlerごとの入力を回収し、`Update()` が `result.Apply(CurrentState, this)` によって更新する。つまり入力スレッドが1000Hzでも、Updateの実行とキュー処理による遅れは残る。

`InputManager.GetPendingInputs()`には、マウス位置の複数供給源を優先度で調停する仕組みと50msの `mouse_source_debounce_time` がある。これはペン座標の更新周期ではない。OTD/SDL Pen/マウスで位置入力が重複すると、ソース切替やカーソル座標の飛びを生み得る。`OpenTabletDriverHandler`は `Window.ClientSize` と出力領域から絶対座標を計算し、筆圧の押下・解除には0.02の半幅ヒステリシスを使う。領域、回転、フォーカス、筆圧閾値まで含めて入力状態を固定する。

採る構成は O3C 1000Hz、ゲーム内蔵OTDによるペン絶対座標、外部OTD Daemon無効、Waylandネイティブ、既存のフルスクリーン領域である。USBの`mousepoll`だけを変更してキーボード・ペンタブの実サンプリングレートが変わったと判断しない。生のペンレポート、evdev、SDL受信、キューenqueue、キューdequeue、判定の各時刻を独立に観測する。カーネル時刻と.NETのStopwatch等のクロックドメインは校正し、`DateTime.Now`で差分を計算しない。物理スイッチ押下時刻はソフトウェア単独では取得できず、外部測定器による基準が必要である。

## 4. Audioを、ゲームクロックからDACまで追う

楽曲は `TrackBass` が `Bass.CreateStream(StreamSystem.NoBuffer, ...)` によりデコードストリームを生成し、テンポ・逆再生等の処理を経てミキサーに接続する。一方ヒットサウンドはサンプル再生イベントであり、楽曲の継続再生と同一のタイミング特性を持つとは限らない。`AudioManager`は`TrackMixer`と`SampleMixer`を持ち、`AudioThread`が通常1000Hz目標でマネージャの `Update()`を呼ぶ。このAudio Threadの周期と、BASSがPCMを書き込む周期は独立している。

`AudioManager.InitBass()`では通常 `Bass.DeviceBufferLength = 10`、`Bass.UpdatePeriod = 5`、`Bass.PlaybackBufferLength = 100`、`Bass.DeviceNonStop = true` を設定する。実験用環境変数 `OSU_TEMP_TESTING_BASS_CONFIG_DEV_PERIOD` を読む分岐では、BASSの `DevicePeriod` と `DeviceBufferLength = 1` を設定する。`-64`は64フレーム指定であり、48kHzなら約1.333ms周期を要求するが、実際のデバイス/ALSA設定がその要求を採用する保証はない。

ゲーム時間の経路も重要である。`FramedBeatmapClock`は `DecouplingFramedClock → InterpolatingFramedClock(DriftRecoveryHalfLife=80) → OffsetCorrectionClock → FramedOffsetClock` を使う。Linuxでのプラットフォーム補正は実装上0として扱われるが、ユーザーOffsetや譜面ごとのOffsetは適用される。`FrameStabilityContainer`はクロックの前後移動と不規則な時間進行を制御し、必要に応じて複数のUpdateを実行する。`FrameStabilityContainer`を単純なFPSリミッターとして無効化するのは誤りである。

出力は `BASS → ALSA PCM` が入口であり、neko5の実測では `PipeWire ALSA互換 → PipeWire Graph → ALSA kernel（snd_hda_intel）→ ALC257 → DAC` と確定した。`ALSA hw → kernel → DAC` は比較実験用の未採用経路。ALSA PCMの実効値は `MMAP_INTERLEAVED / S32_LE / 2ch / 48000Hz / period_size=1024 / buffer_size=32768`。PipeWireの設定メタデータは `clock.quantum=1024`、`clock.force-quantum=0` である。14:31のpw-topはC・QUANT=0だったが、15:30の追試ではALC257ドライバがR/256/48000と観測された。これでGraph周期の適用は確認できたが、開始時ERR0→12の原因、BASS周期、音響遅延の改善は未確認。`snd_pcm_period_elapsed()`はハードウェアがperiodを処理したときにPCMランタイムと待機ユーザー空間を更新する。ALSAのperiod_size、buffer_size、hw_ptr、XRUNを記録する。

1msのAudio Thread、1msのBASSデバイス周期、1msのPipeWire quantum、1msの発音遅延は別の概念である。PipeWireの`clock.power-of-two-quantum`が有効なら48フレーム要求が32等に丸められる場合がある。1msちょうどを自己目的化せず、楽曲の時間安定性、ヒットサウンドの発音開始ジッター、XRUN、物理発音の時刻を比較する。SplitCastのためにゲームのローカル出力経路を迂回させない。PipeWireによる独立した音声複製が安定するならDirect ALSAの排他的占有より適する。

## 5. Updateの本体：クロック、判定、描画ノード生成

`GameHost.UpdateFrame()`は `Root.UpdateSubTree()`、`Root.UpdateSubTreeMasking()`、`Root.GenerateDrawNodeSubtree(frameCount,...)` を順に実行し、Draw Thread向けスナップショットを書き込む。`FrameStabilityContainer`による時間進行、`OsuInputManager`を通った入力、各HitObjectの状態更新、HitWindowによる判定、スコア更新、アニメーション/スキニングの更新は全て同一のリソース予算に入る。UpdateのFPSが高くても、あるフレームでGCやアセットロードが発生すれば入力状態の適用が遅れる。

`GameHost.Run()`はデスクトップで `.NET GCSettings.LatencyMode = SustainedLowLatency` を設定する。ここから、すべてのGC停止がなくなるわけではない。入力キューの長さ、Updateフレーム時間、DrawNode生成時間、GC pause、スケジューラrunqueue遅延を同時に観察する。譜面・スキン・Mod・背景動画・ストーリーボード・ヒットオブジェクト数、画像/テクスチャ生成、ヒットサウンド同時発火数を変更する場合は、それを「別ワークロード」として扱う。

`FrameSync`の実装は表示リフレッシュレートをRとして、`Limit2x`なら Draw=min(2R,1000)、Update=min(4R,1000)、`Limit4x`なら Draw=min(4R,1000)、Update=min(8R,1000)、`Limit8x`なら Draw=min(8R,1000)、Update=min(16R,1000)となる。`Unlimited`は通常実行ではDraw/Updateとも最大1000Hzを目標とする。VSyncやVRRでは別の設定値を使用する。これは上流の`GameHost.updateFrameSyncMode()`から求められる理論的な上限であり、実際のUpdateとDrawが同じ周波数で安定動作する保証ではない。

Updateの最適化において、最初に手を入れるのはカーネル設定ではない。原則はアセットのプリロードと同期IO回避、1フレーム内の割り当てとGC原因の特定、描画ノード生成コストの分離、ゲーム外プロセスの干渉排除である。頻度だけを増やすための既定上限パッチは行わない。スケジューラレベルの変更は、具体的なrunqueue遅延が立証された場合に検討する。

## 6. Drawを、GPUドライバから物理走査まで追う

Updateが生成したDrawNodeは `TripleBuffer<DrawNode>` を介してDraw Threadに渡る。Drawは `Renderer.BeginFrame()`、opaque pass、depth testを使うback pass、`Renderer.FinishFrame()`、`Renderer.SwapBuffers()`を実行する。`GLRenderer`は `SDL3GraphicsSurface.SwapBuffers()`を呼び、その実装は`SDL_GL_SwapWindow()`。Wayland上のOpenGL環境ではEGL/Waylandバッファがコンポジタへ提供される。

極めて重要なのは、`GameHost.Swap()`がOpenGLかつVSync有効時に `Renderer.WaitUntilIdle()`を呼ぶ点だ。GLRendererでの実体は `GL.Finish()`。GPU命令の完了待ちはCPUをブロックする可能性があり、Draw Threadのトレースに含める。`GLRenderer.WaitUntilNextFrameReady()`は空実装なので、別レンダラーのフレーム待機構造をそのままGLに当てはめない。

その後はMesaのGLドライバ、Intel i915のバッファ管理・同期、Waylandのsurface commit、Hyprland、DRM/KMS atomic commit、CRTCのページフリップ、eDP伝送、LCDの走査・応答へ進む。Direct ScanoutはHyprlandの描画合成を回避できる条件下で成立するが、OpenGLやMesa、GPUのレンダリング、Waylandプロトコル、KMSのフレーム提示まで消えるわけではない。機能が設定されていることと、各ゲームフレームでDirect Scanoutが成功していることも違う。

ゲーム側1280×720と内蔵パネルの物理走査解像度は別である。実機eDP-1は1366×768@60.003Hz、scale=1、VRR=false、XRGB8888で確定。osu!ウィンドウは1366×768・native Wayland・fullscreen=2。今回の前面プレイ観測で `directScanoutTo` は8/8回有効、`directScanoutBlockedBy` はnull。旧採取時の `directScanoutTo=0` は非アクティブワークスペースのため失敗判定から除外。`activelyTearing=false`であるためDirect Scanoutと tearing の有効化を混同しない。表示スキャンの時間はリフレッシュレートRなら1/R秒で、画面上部と下部で照射時刻が異なる。ドライバのpage flip完了時刻とピクセルが発光する時刻も同一ではない。

現時点でOpenGL・native Wayland・1280×720・Direct Scanoutの成立条件を固定し、Vulkan/Zink/Gamescopeを追加しない。`AllowTearing`、VSync、VRR、ゲームのFrameSync、Hyprlandの即時表示規則が一致しているか確認する。撮影・通知・ポータル・フロートウィンドウがDirect Scanoutを解除するか、KMSイベントとGPU利用率を使って確かめる。

## 7. Linuxカーネルと共有物理資源の深部

入力ではxHCI割込み、USBホストコントローラー、HID URB、`input_event`、evdevリングバッファ。音声では`snd_pcm_period_elapsed`、HDA/SOF DMA、PCMリングバッファ、割込みとPipeWireのRTスレッド。描画ではi915 GEM/メモリ確保、GPUコマンド投入、fence、DRM atomic commit、vblank/page flip。さらに全系統がCPUスケジューラ、キャッシュ、DRAM、電力・温度制約を共有する。

特にi5-10210Uは4コア8スレッド、公称15W（構成可能10〜25W）、Intel UHD GraphicsとCPUは電力・メモリの制約を共有する。実機ではLinux 7.3.0 PREEMPT_DYNAMIC、intel_pstate/performance。以前の採取ではcpu0約4.09GHz、Package温度86℃だったが、今回は8サンプルでcpu0約2.900–3.083GHz、Package温度95–98℃。14:31だけでは熱スロットリングとは断定できなかったが、15:30の追加採取でカウンター+4を確認した。音声量子・温度・フレーム尾部遅延の因果関係とAPERF/MPERF、RAPLによる内訳はなお未取得。`performance` governorだけで最大Turbo固定を保証することもない。

カーネル最適化の候補は、スケジューラのrunqueue待機、USB/HDA/i915割込み遅延、CPUFreqとC-state復帰、GPU/CPU共有帯域、キャッシュミス、ハードウェアの電力・熱制限、ページフォルト、zramスワップに分解する。`SCHED_FIFO`、全CPU isolation、PREEMPT_RT、C-state完全無効、IRQ affinity固定、全USB autosuspend無効は、各仮説に対応するトレース結果なしで適用しない。CPUが4コアしかないため、ひとつの改善が別系統を大きく悪化させ得る。

入力のハードウェア報告を `usbmon`、evdevを `evtest`、スケジューラを`sched_switch`/`sched_wakeup`、CPU電力を`turbostat`/RAPL、GPUを`intel_gpu_top`、DRMをatomic/vblankトレース、音声を`pw-top`とALSA `hw_params`で確認する。短時間の高度なトレースはそれ自体が負荷を生むので、計測用セッションと普段の性能比較を混ぜない。

## 8. SplitCastを競技処理に干渉させない理想形

neko5はゲームの描画とローカル音声再生を完結させる。neko7は受信した映像・音声の復元、AV同期、配信シーン、オーバーレイ、TTS、OBS、録画、外部出力を担当する。ゲームの描画パイプライン内部へOBSフックを追加せず、画面キャプチャは可能ならKMSフレームバッファの参照から分岐する。KMSアクセスには権限の問題があるため、最小機能の権限分離されたヘルパーがDRM情報を取得し、一般権限のワーカーへ必要なバッファ記述だけを渡す。

DMA-BUFを利用できてもコピーが必ずゼロになるわけではない。フォーマット／modifier互換性がなければGPUコピーや色変換が発生する。キャプチャがスキャンアウトバッファを長く参照すると、バッファの再利用・描画・表示の妨げにもなる。したがって、キャプチャはゲームのSwapやKMS page flipを待たせず、十分な速度で自分の所有するリソースへ渡し、遅延が累積した映像は古いフレームから捨てる。キャプチャ手段がDirect Scanoutを解除するなら、その手段は不採用とする。

Intel Quick Sync/VAAPIのH.264エンコードを第一候補にする。ただしCPUから独立した専用の固定機能エンジンを利用しても、メモリ帯域、GPU周辺処理、電力・熱、ドライバ割込みは共有する。Intel iHDの対応プロファイルは`vainfo`と実エンコードで確認する。エンコード自体をneko7へ移すために非圧縮720p60を送る構成は、帯域と転送CPU負荷が増える可能性があるため無条件の最適解ではない。

ゲーム音声は `BASS → PipeWire → 内蔵DAC` を主経路とし、PipeWireのモニター／キャプチャストリームで独立に複製する。音声キャプチャはローカル出力が正常な限り常に非ブロッキングである必要がある。マイクは別ストリームとして扱い、ゲーム音とミックスしてから転送するか、neko7側で合成するかを選択できるようにする。原則は遠隔側での合成。低遅延のゲーム音声にリモート通信往復を挟まない。

映像と音声はneko5上で同じ計測可能な単調時刻系へ対応づけ、各パケットにPTSと連番を付ける。neko5のCLOCK_MONOTONICとneko7のCLOCK_MONOTONICの数値をそのまま引き算してはいけない。RTP timestamp/RTCP sender report等を利用してクロック対応とドリフトを推定し、neko7でreorder、jitter buffer、欠落処理、AV同期を行う。映像の古いフレームは捨てられるが、音声は不連続を明示して適切な補間・隠蔽を使う。通信の輻輳やneko7のOBS停止がneko5のゲームスレッドまで伝播してはならない。

SplitCastの各機構はneko5のゲームとは独立したsystemd cgroupとプロセスに配置する。制御用プロセス、KMS helper、ビデオキャプチャ、VAAPI encoder、PipeWire monitor、mux/送信、監視器を分割する。最低限のCPUWeight/IOWeight、メモリ上限、キャプチャ専用の有限キュー、停止時の権限撤去、ゲーム起動と関係のない再接続処理を備える。ただしCPUWeightではGPUやメモリ帯域を完全隔離できない。ゲーム性能の回帰が検出されたら、まず映像取得頻度、キャプチャ解像度、エンコーダ負荷を下げ、それでも回避できなければSplitCastを停止する。ゲーム設定や音声出力経路を勝手に変更しない。

ハードウェアを追加せずに画面と音声をキャプチャする以上、ゼロCPU・ゼロGPU・ゼロメモリ・ゼロIRQ負荷は物理的に保証できない。「ゲームを一切損なわない」は理想的な優先制約であり、実装では測定可能な回帰を検知して即座にキャプチャを止める設計が最も近い。録画や配信の連続性より、入力・音声・更新・描画の性能を優先する。

## 9. osu!lazerの性能上限から導く採用試験

単独プレイを基準に、まずFrameSync各モードでアプリのUpdate/Drawフレーム時間と、実ディスプレイ提示時刻を観測する。上流実装の1000Hz上限は「最大更新目標」で、neko5が現実に達成できる上限は条件ごとの計測結果から求める。評価軸は平均FPSだけでなく、Input enqueue→dequeue→judgement、Audio XRUNと発音開始ジッター、UpdateとDrawのp50/p95/p99/p99.9、GPUのキュー待ち、実scanoutの成功率、温度上昇による周波数低下である。

測定は同一のosu!lazerビルド、譜面、Mod、スキン、1280×720、パネルモード、電源状態、温度条件、音声出力装置で比較する。Update/Draw比較にはリプレイ再生等の再現可能な負荷を用い、Inputだけは物理操作の再現性を管理する独立実験を用意する。時間の経過で熱状態が変わるので、A/Bを交互に戻して確認する。キャプチャの有無を比較するときも、neko5の使用時間、CPU・GPU負荷、入力・音声の実際の結果を測る。

棄却条件は、入力イベントの欠落・順序異常、音声XRUN、Draw/Updateの尾部遅延の悪化、Direct Scanoutの解除、競合による長時間の熱スロットリング、再現性のない「体感だけの改善」。固定遅延が短くても、p99.9が悪化する設定は競技性能を損ね得る。数値を比較するときはサンプル数と測定誤差を提示し、実機未測定の値を最適値として採用しない。

最初のインベントリはユーザーが実機で実行し、20ファイルを正本として提出済み。コーデックALC257、ドライバsnd_hda_intel、60.003HzのeDP、O3CとCTL-472の接続ポート、PipelineのPipeWire ALSA経路は確定した。Direct Scanoutはosu!アクティブ時8/8サンプルで成立（確認済み）。現有のUSBエンドポイントはO3C 1ms／CTL-472 2ms。残る不足は実HIDレポート間隔、XRUN/Audio実遅延、CPU/GPUの連続負荷、キャプチャ時のDirect Scanout維持、neko7 RTT/帯域、ゲームビルド等である。以前の20ファイルを再取得させず、追加採取は `scripts/osu-performance/collect-active.sh` で再現可能なスナップショットを取得する。ただし真のframe-timeや音声XRUNを測るには別途計装が必要。これらが揃う前に個別のカーネルパラメータやSplitCastエンコーダ設定を恒久化しない。
