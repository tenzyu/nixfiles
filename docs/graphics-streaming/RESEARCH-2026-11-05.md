# osu!lazer／NixOS／Wayland／Hyprland／OBS／SplitCast ドメイン知識

調査基準日: 2026-11-05。GitHub の main / master、公開された実装、提供された実機ログと操作報告を根拠にした技術解説。設計上の可能性、機能テスト、実機での性能検証を区別する。

## 1. システム境界と要求

対象は `neko5`（Dynabook BJ65/FS、Core i5-10210U、Intel 統合 GPU、NixOS、Hyprland、osu!lazer、ペンタブレット）と、離れた場所の `neko7`（RTX 4060 Ti 8GB、NixOS、SplitCast の制作・配信側）である。両者は SSH と Tailscale で連携する。ユーザーが明示した不変条件は、osu!lazer の OpenGL と native Wayland を維持すること、Vulkan／Zink を解決策にしないこと、1280×720 のゲーム内設定・入力領域を保つこと、Direct Scanout を維持すること、ゲームを録画・配信するために入力性能を犠牲にしないこと、追加の月額支出を発生させないことである。

これまで実機で確かめられた操作結果として、osu! の解像度を 1280×720、ゲーム側を Fullscreen とし、さらに Hyprland で `Win+F` を押せば、望む入力比率と表示品質のまま Direct Scanout が成立する。この成功条件を再検証対象に戻さない。GitHub にある設定と実機の NixOS 世代は同一とは限らず、パッチ適用済みかどうかを推測しない。

概念上の入力経路は `USB HID → Linux のデバイスノード・udev → osu.Framework の OpenTabletDriverHandler → ゲーム状態`。画面表示は `osu.Framework の OpenGL 描画 → SDL3/EGL → Wayland の surface/buffer → Hyprland → DRM/KMS → Intel iGPU/display`。キャプチャ・配信はこの表示経路のどこかから分岐し、ローカル GPU エンコード、伝送、neko7 のデコード／OBS 合成／エンコードへ進む。

「native Wayland」「Direct Scanout」「内蔵 OTD」「GPU エンコード」は別々の最適化軸である。Wayland ネイティブだから無合成ではない。Direct Scanout が成立してもペンの入力遅延を直接計測したことにはならない。GPU エンコードはエンコード処理の担当を示すだけであり、画面取得・コピー・同期・色変換のコストが消えることを意味しない。

## 2. 入力: osu.Framework 内蔵 OpenTabletDriver の本体

`osu.Framework/Platform/SDLGameHost.cs` は `KeyboardHandler` の次に `OpenTabletDriverHandler` を登録しており、SDL3 の場合には `PenHandler` も追加する。前者がゲーム内蔵の OTD、後者が SDL3/OS 側から渡る外部ペン入力を扱う。両者は単一の「OTD モード」ではない。ゲームの設定項目でも `Tablet` と `Tablet (External)` が別の入力サブセクションとなる。

`OpenTabletDriverHandler.Initialize()` は有効化時に `TabletDriver.Create()` を呼ぶ。`TabletDriver` は OTD の `Driver` を継承し、`DriverServiceCollection` から必要なサービスを生成する。デバイス追加時の検出、Vendor ID と既知のタブレット設定との照合、入力エンドポイントからの `Report` イベント登録をゲームプロセス内で実行する。外部 `otd-daemon` への RPC を行う設計ではない。

ゲーム内の `AbsoluteTabletMode` は `IAbsolutePointer` を受けてイベントを流す。ペンの位置は `MousePositionAbsoluteInputFromPen`、相対入力は `MousePositionRelativeInputFromPen`、筆圧しきい値による接触は `MouseButtonInputFromPen` に変換する。`handleDeviceReported()` は `ITabletReport` と `IAuxReport` を扱い、ペンボタンと補助キーもゲームの入力キューに送る。`enqueueInput()` にはゲームウィンドウがアクティブかどうかの判定がある。これは OS の仮想マウスを通す経路とは異なるが、経路の短さだけで実測遅延の優劣は確定しない。

ペンタブの物理領域の幅・高さ、中心、回転、出力領域は `AreaSize`／`AreaOffset`／`Rotation`／`OutputAreaSize`／`OutputAreaOffset` などで管理する。`updateOutputArea()` は osu! ウィンドウの `ClientSize` を基準に出力領域を計算し、ウィンドウの `Resized` イベントでも更新する。したがって、ゲーム内で表示バッファの寸法が変わったとしても、物理入力領域の設定値まで自動的に 1366×768 へ変更されるわけではない。`ScalingMode.Everything` を使うと、ゲーム内表示領域へのペン座標制約も合わせて変わるため、単なるウィンドウ解像度より入力座標系への影響が大きい。

根拠: [SDLGameHost.cs](https://github.com/ppy/osu-framework/blob/master/osu.Framework/Platform/SDLGameHost.cs)、[OpenTabletDriverHandler.cs](https://github.com/ppy/osu-framework/blob/master/osu.Framework/Input/Handlers/Tablet/OpenTabletDriverHandler.cs)、[TabletDriver.cs](https://github.com/ppy/osu-framework/blob/master/osu.Framework/Input/Handlers/Tablet/TabletDriver.cs)、[AbsoluteTabletMode.cs](https://github.com/ppy/osu-framework/blob/master/osu.Framework/Input/Handlers/Tablet/AbsoluteTabletMode.cs)、[TabletSettings.cs](https://github.com/ppy/osu/blob/master/osu.Game/Overlays/Settings/Sections/Input/TabletSettings.cs)。

## 3. Linux のデバイスアクセスと NixOS の外部 OTD

「内蔵ドライバーが存在する」と「通常ユーザーがペンタブのデバイスノードを開ける」は別の問題だ。OTD ライブラリはデバイスを検出・読み取りするため、機種に応じた HID/hidraw/libusb 系デバイスへの権限が必要になる。udev ルールはデバイス生成時のアクセス権やタグを設定する。外部 OTD を導入してから内蔵 OTD が動いたという経験は、外部 Daemon が必須だったことの証明ではなく、同時に導入された udev ルールやカーネルモジュールの扱いで説明できる。

nixpkgs の `nixos/modules/hardware/opentabletdriver.nix` では、`hardware.opentabletdriver.enable = true` により、`environment.systemPackages` へのパッケージ追加、`services.udev.packages` の登録、`boot.blacklistedKernelModules`（既定は `hid-uclogic` と `wacom`）、`systemd.user.services.opentabletdriver` の設定が有効になる。`hardware.opentabletdriver.daemon.enable` の既定値は `true`。そのため、Daemon だけを止めたい場合には `enable = true; daemon.enable = false;` が最小変更となる。

外部 OTD の公式 Linux 権限資料には `/dev/uinput` も登場する。これは外部 Daemon が OS に仮想入力イベントを出す用途を含むためで、ゲーム内蔵の絶対座標イベント経路が必ず `/dev/uinput` を必要とすることを意味しない。デバイス読み取りに必要なノードと、仮想入力出力に必要なノードは分離して精査する。この設定は外部 OTD パッケージそのものをシステムから除去する設定ではない。udev ルールの供給元として引き続きパッケージを参照する。反対に `enable = false` にすると、必要な権限設定も同時に失われるため、内蔵 OTD が使えなくなる可能性がある。機種限定の udev ルールに分解する場合は実際の VID/PID、HID ノード、アクセス権限を先に調べる必要がある。kernel module blacklist は、他のペン入力デバイスにも影響し得る。

ユーザーのリポジトリには `modules/50-features/open-tablet-driver.nix` があり、元の定義は `hardware.opentabletdriver.enable = true;` だった。前段で作成したパッチはこれを attribute set に置き換えて `daemon.enable = false;` を追加するだけである。実際の NixOS への反映やペン入力の動作までは確認されていない。

検証では、先に `systemctl --user stop opentabletdriver.service` で外部 Daemon を一時停止し、`pgrep -af 'otd-daemon'` と osu! の `Tablet` 検出状態を調べる。デスクトップ上のペンカーソルは動かなくなる可能性があるが、osu! 内蔵 OTD の動作とは別の問題となる。復旧経路として `systemctl --user start opentabletdriver.service` を保持する。NixOS の `nh os build` はビルドであり、サービスを切り替える操作ではない。`nh os switch` 後の挙動を別途確認する。

根拠: [NixOS OTD モジュール](https://github.com/NixOS/nixpkgs/blob/master/nixos/modules/hardware/opentabletdriver.nix)、[OTD Required Permissions](https://opentabletdriver.net/Wiki/Documentation/RequiredPermissions)、[NixOS マニュアルの OTD オプション](https://nixos.org/manual/nixos/unstable/options.html)。

## 4. osu! のフレーム処理と OpenGL

`osu.Framework` の `GameHost` は、入力・ゲーム更新・描画・表示を管理する。GPU に命令を渡した時刻、GPU が描画を完了した時刻、画面のリフレッシュ時刻は同じではない。描画結果は swapchain のバッファを通って compositor とディスプレイに渡される。バッファ待ち、VSync、FIFO、VRR、GPU コマンドの同期点が入力表示遅延の主要な変数になる。

OpenGL 実装の `GLRenderer` では `SwapBuffers()` が SDL/OpenGL surface の swap に委譲される。`WaitUntilNextFrameReady()` は空実装で、`WaitUntilIdle()` は `GL.Finish()` を実行する。ただし `GL.Finish()` が毎フレーム必ず呼ばれるという意味ではなく、実際の呼び出し箇所と frame synchronization 設定を区別する必要がある。`GL.Finish()` は GPU コマンドの完了待ちを生む同期バリアで、無条件に増やせば待ち時間が増え得る。

`GameHost` のコードには `Renderer.AllowTearing = windowMode == WindowMode.Fullscreen && !isVrr` に相当する条件があり、ゲーム側での tearing 許可はウィンドウモードや VRR と関係する。一方、Hyprland 側の `immediate = true` は compositor が tearing 候補を許可する側の条件であり、ゲームが必ず即時表示することを保証しない。GPU ドライバー、Wayland presentation/swap のモード、KMS 出力の能力、VRR の状態も関わる。

`OSU_GRAPHICS_RENDERER`、`OSU_GRAPHICS_SURFACE`、`OSU_SDL3` などは osu.Framework が参照する環境変数である。OpenGL を明示する必要があるなら `OSU_GRAPHICS_RENDERER=opengl OSU_GRAPHICS_SURFACE=OpenGL` のように指定できるが、実際のレンダラーが既に OpenGL なら、指定を増やしても性能改善の証拠にはならない。`SDL_VIDEODRIVER=wayland` の指定は Wayland のビデオバックエンドの選択であって、レンダラーを Vulkan にする操作ではない。ゲームの実ログにある `SDL3 Video driver: wayland` と GL renderer を別々に確認すべきである。

根拠: [GLRenderer.cs](https://github.com/ppy/osu-framework/blob/master/osu.Framework/Graphics/OpenGL/GLRenderer.cs)、[GameHost.cs](https://github.com/ppy/osu-framework/blob/master/osu.Framework/Platform/GameHost.cs)、[FrameworkEnvironment.cs](https://github.com/ppy/osu-framework/blob/master/osu.Framework/FrameworkEnvironment.cs)、[SDL3 環境](https://wiki.libsdl.org/SDL3/README-wayland)。

## 5. 解像度と二重 Fullscreen 状態

問題を理解するには、4種類の寸法・状態を分ける必要がある。osu! 設定の Fullscreen resolution（1280×720）、SDL3 が管理する window size と pixel/drawable size、Hyprland が管理する logical size と物理モニターの pixel size、そしてタブレット入力に適用されるゲーム内座標系である。これらは常に一致しない。

`osu.Game/OsuGame.cs` は初期の `WindowMode` を macOS 以外で `Fullscreen` にする既定値を定義しているが、保存済み設定によって上書きされる。`SDL3Window.Windowing.cs` は `Fullscreen` を `SDL_SetWindowFullscreenMode(closestMode)` と `SDL_SetWindowFullscreen(true)` へ、`Borderless` を `SDL_SetWindowFullscreenMode(NULL)` と `SDL_SetWindowFullscreen(true)` へ振り分ける。`Fullscreen` では表示可能なモードを `SDL_GetClosestFullscreenDisplayMode()` から選び、`SizeFullscreen` の既定値 9999×9999 には native size 採用という特別な意味がある。Wayland の論理画素と物理画素、pixel density の差を補正する分岐も実装されている。

SDL3 の Wayland バックエンドは Fullscreen 要求をクライアントから compositor に送るが、実際のサイズ変更は非同期であり、拒否されることもある。さらに画面内の scaling を行うかどうかは `SDL_VIDEO_WAYLAND_MODE_SCALING`、compositor の viewport 対応などに左右される。`Borderless` は一般的には扱いやすい選択肢だが、既に成功している 1280×720／Fullscreen／`Win+F` 構成を置き換える根拠にはならない。

Hyprland には compositor 内部の Fullscreen 状態（internal）と、クライアントへ伝える Fullscreen 状態（client）がある。`0` はなし、`1` は最大化、`2` は Fullscreen。現在の `Win+F` は `hl.dsp.window.fullscreen_state({ internal = 2, client = 0 })` へ割り当てられている。つまり compositor は窓を全面に配置しつつ、アプリには Fullscreen と報告しない。osu! が UI 上で Fullscreen と設定されていることと、Hyprland が client=0 を保つことは、別レイヤーの状態である。

ユーザーはこの状態で Direct Scanout と適切な入力比率が成立することを実機で確認済み。したがって問題は「1280×720 を捨てること」ではなく、手動の `Win+F` に相当する状態を初回マップ時に再現することだ。既存の `window_rule` の `fullscreen = true` は内部状態だけを定義する可能性があり、`internal=2, client=0` と同じ契約ではない。静的ルールの `fullscreen_state = "2 0"` は上流ソースでサポートされており、候補として具体的である。ただし SDL3 側からの後続 Fullscreen 要求が実際の状態を変えるか、ルールが適切な class にマッチするかは実機未確認である。

1366×768 と 1280×720 のアスペクト比はそれぞれ約 1.778646 と 1.777778、差は約 0.0488%。見た目の歪みがほぼ分からなくても、物理ピクセル数は 1,049,088 と 921,600 で約 13.83% 異なる。見た目の近さを、GPU バッファサイズの一致と取り違えないことが重要だ。

根拠: [osu! デフォルト](https://github.com/ppy/osu/blob/master/osu.Game/OsuGame.cs)、[SDL3Window.Windowing.cs](https://github.com/ppy/osu-framework/blob/master/osu.Framework/Platform/SDL3/SDL3Window.Windowing.cs)、[SDL_SetWindowFullscreen](https://wiki.libsdl.org/SDL3/SDL_SetWindowFullscreen)、[Hyprland dispatcher](https://wiki.hypr.land/configuring/core/dispatchers/)、[Hyprland window rules](https://wiki.hypr.land/configuring/core/rules/window-rules/)。

## 6. Direct Scanout の厳密な成立条件

Direct Scanout は Wayland を使わないことではない。クライアントが Wayland surface に attach した GPU バッファを compositor が評価し、DRM/KMS に直接渡す経路である。一般的な compositor 合成なら、複数 surface を compositor のレンダーターゲットへ描画して KMS に送る。Direct Scanout ではその追加の合成レンダーパスを省ける。ただし出力の atomic commit、表示タイミング、カーソルプレーン、フェンス、バッファ寿命の管理は残る。zero-copy の成立も処理経路・実装ごとに吟味する。

Hyprland の `CMonitor::isSolitaryBlocked()` は、fullscreen window の有無、special workspace、通知、overlay layer、透過、浮動ウィンドウ、surface の不透明性、サイズ、アニメーションなどを調べる。`CMonitor::isDSBlocked()` は設定、ミラー出力、画面録画、software cursor、単独表示候補、surface、transform、DMA-BUF と色管理等を検査する。重要な条件のひとつは `surface.bufferSize == monitor.pixelSize` と transform の一致である。ここでいう bufferSize は、osu! 設定画面の「解像度」の保存値ではない。

ユーザーの操作で Direct Scanout が成立しているなら、当該フレームでの有効なバッファ／モニター条件は満たされたと考えられる。この観測は「保存済みのゲーム内 Fullscreen resolution が 1280×720 だから出力バッファも絶対に 1280×720」という以前の推定を否定する。実際に `Win+F` の前後でどの層の寸法が変わったかは別途記録しない限り確定できないが、ゲーム内設定の値と最終バッファの寸法は別管理である。

`hyprctl monitors -j` には `directScanoutTo`、`directScanoutBlockedBy`、`solitaryBlockedBy`、`activelyTearing` などが出力されるバージョンがある。`directScanoutTo` は使用中の surface を表す識別子で、`0` は使用していない。`directScanoutBlockedBy: null` は前提条件を阻害する理由がないことを示すが、それだけで scanout commit が成功したとは限らない。`directScanoutBlockedBy` と `directScanoutTo` を合わせて見る。`direct_scanout = 1` は試行を許可する設定であり、「常時成功」のスイッチではない。

`mako` が overlay layer に通知を表示すると、Hyprland が単独 surface とみなせない場合がある。Waybar、他の overlay、ソフトウェアカーソル、色変換、スクリーンキャストも干渉要因になる。`mako` を `overlay` から `top` に変更するパッチは表示の優先順位を変えるが、それだけであらゆる通知の Direct Scanout 干渉がなくなるとは保証できない。`hypr-gaming-mode` は mako の停止や waybar の `SIGSTOP` まで実行する構成だったため、切り替えと復旧の安全性を別に検討する必要がある。

根拠: [Hyprland Monitor.cpp](https://github.com/hyprwm/Hyprland/blob/main/src/output/Monitor.cpp)、[Hyprland monitor IPC](https://github.com/hyprwm/Hyprland/blob/main/src/ipc/s1/Commands.cpp)、[モニター表示](https://wiki.hypr.land/configuring/core/monitors/)、[Direct Scanout 設定](https://wiki.hypr.land/configuring/core/config-options/)。

## 7. OBS Game Capture と OpenGL フック

`obs-vkcapture` は、OBS 側に追加する Game Capture source と、ゲームプロセスへ注入する capture client から構成される。`obs-gamecapture` のシェルラッパーは `LD_PRELOAD` で `libobs_glcapture.so` を指定し、`OBS_VKCAPTURE=1` も環境へ渡す。ゲームが OpenGL/EGL を使用するとき、フック側は `eglSwapBuffers()` を横取りし、OBS と接続している場合にフレーム取得を開始する。これは画面全体を PipeWire で録画するのと異なり、ゲームの GL swap に介入する方式である。

ソースの `gl_shtex_init()` は、FBO と `GL_RGBA` テクスチャを生成し、`eglCreateImage` により OpenGL texture を EGLImage 化する。その後 `eglExportDMABUFImageQueryMESA` で DRM fourcc、FD 数、modifier を問い合わせ、`eglExportDMABUFImageMESA` でファイルディスクリプタ、stride、offset を取り出す。フレーム取得時には `glBlitFramebuffer` を使うため、キャプチャが必ずコピーなしで済むわけではない。OBS 側は DMA-BUF を import して、自身のテクスチャとして扱う。fd 共有は CPU メモリへの全画素コピーを避けられる場合があるが、GPU コピーや同期が消える保証ではない。

`gl_shtex_init()` に失敗した場合、元の実装は `vulkan_shtex_init()` へフォールバックする。`OBS_VKCAPTURE_GLVULKAN` を設定すると OpenGL の共有テクスチャ経路を初めから回避するコードもある。したがって「OpenGL のゲームである」「`obs-gamecapture` で起動した」だけでは、キャプチャ実装が Vulkan を一切利用しないことの証明にならない。Vulkan 禁止がゲームだけでなくキャプチャ内部にも及ぶなら、OpenGL 専用にフォールバックを削ったビルドが必要になる。今回のユーザー要求では Vulkan／Zink への切り替えを解決策として扱わない。

ゲームを起動しているだけではフックが接続・取得を始めないため、OBS の Game Capture ソースを追加・選択した瞬間に障害が表面化することは実装と整合する。`obs-gamecapture osu-lazer`、単なる `osu-lazer`、OBS を起動せず Game Capture ソースもない状態を、同じ実験と呼ぶことはできない。

根拠: [obs-vkcapture README](https://github.com/nowrep/obs-vkcapture)、[obs-gamecapture.in](https://github.com/nowrep/obs-vkcapture/blob/master/src/obs-gamecapture.in)、[glinject.c](https://github.com/nowrep/obs-vkcapture/blob/master/src/glinject.c)。

## 8. クラッシュの証拠、原因候補、修正境界

2026年11月5日の `neko5` ログでは、`osu-lazer-bin-2026.1005.0` が OBS ソース有効化時に繰り返し `SIGSEGV` で終了している。直近の core（PID 7099）では、`__eglDispatchFetchByDisplay`（Mesa `libEGL_mesa.so.0`）→ `dispatch_eglExportDMABUFImageQueryMESA` → `gl_capture`（`libobs_glcapture.so`）→ `eglSwapBuffers`（同ライブラリ）→ `Wayland_GLES_SwapWindow`（SDL3）という呼び出し列が残る。`exit=139` は一般的に SIGSEGV による 128+11 の終了コードと整合する。`[obs-vkcapture] Texture GL_RGBA 1280x720` はテクスチャを初期化し始めたことを示すだけで、EGLImage 作成、DMA-BUF export、OBS import の完了は表さない。別実行では 1366×768 のテクスチャログも出ていた。

ここから確定するのは、少なくとも最後に観測された `SIGSEGV` はゲーム本体の通常の譜面処理ではなく、ゲームの swap に挿入された OpenGL capture hook から Mesa の EGL export 関数へ進んだ経路で起きた、という点である。`libobs_glcapture.so` の関与は強いが、根本原因はまだ確定しない。`EGLDisplay` が無効、EGL/GLVND のディスパッチとライブラリが整合しない、EGLImage のコンテキスト／テクスチャの所有関係が不正、Mesa 側に不具合がある、という仮説を区別する必要がある。`eglGetProcAddress()` の返り値が単純に NULL だったという仮説は、ディスパッチ関数内部までスタックが進んでいることから優先度が低い。

`libEGL_mesa.so` と `libobs_glcapture.so` の混在が実際に不整合を起こしたとはまだ証明されていない。`libgallium-26.1.8.so` が別スレッドのスタックに見えるのは Mesa の実装が稼働していたことを示すが、それだけで Mesa 26.1.8 固有のバグとは断定できない。`libobs_glcapture.so without build-id` もシンボル解析の制約であって、それ自体がクラッシュ原因ではない。

最小の再現・切り分けでは、同じ NixOS 世代、同じ Mesa、同じ osu! ビルド、同じ OpenGL/Wayland を保つ。Game Capture を選ぶ前に `/proc/<PID>/maps` の `libEGL`、`libGLdispatch`、`libobs_glcapture` を列挙し、どの実体がロードされたか確認する。`/proc/<PID>/environ` は `LD_`、`EGL_`、`MESA_` など該当する変数だけに絞り、パスワードやトークンを含む全環境を公開しない。必要なら `coredumpctl debug` とデバッグシンボルを使い、落ちたスレッドの `bt full`、共有ライブラリの一覧、引数、EGL error と拡張サポートを調べる。

上流で対処するなら `glinject.c` の EGL display、current context、EGLImage、拡張関数の解決元を明示的に記録し、DMA-BUF export 不能ならゲームを巻き込まずキャプチャだけ停止するよう、失敗経路とフォールバックを再設計する。ただし、今回のクラッシュは関数がエラーを返す前に起きている。単に呼び出し後の返値検査を追加しても防げないため、呼び出し前の検証と初期化モデルの修正が必要となる。

1.5.5 から 1.5.6 の公式ソース差分には、該当する EGL export の GL 経路修正が含まれていない。バージョンを上げるだけで直るとは判断できない。別の native Wayland/OpenGL アプリでもフック時の問題報告は存在するが、それらは今回と同一の根本原因を立証するものではない。

根拠: 実機提供の `coredumpctl` 出力、[glinject.c](https://github.com/nowrep/obs-vkcapture/blob/master/src/glinject.c)、[1.5.5→1.5.6 差分](https://github.com/nowrep/obs-vkcapture/compare/v1.5.5...v1.5.6)、[別アプリの OpenGL/Wayland 事例](https://github.com/nowrep/obs-vkcapture/issues/216)。

## 9. PipeWire、GSR、DRM/KMS と Direct Scanout の干渉

キャプチャ方式は少なくとも3つある。第一に OBS の `Game Capture` はゲームプロセス内部の EGL swap にフックする。第二に OBS の PipeWire 画面共有は XDG Desktop Portal を経由して Hyprland に画面共有を要求する。第三に GPU Screen Recorder（GSR）の物理モニター指定は DRM/KMS などの画面キャプチャ経路を用いる。これらはフック位置も、権限・保護境界も、必要な GPU 処理も異なる。

Hyprland の Direct Scanout 判定には `Screenshare::mgr()->isOutputDSBlocked()` があり、portal を通した画面共有は `screen record/screenshot` のブロッカーになる可能性が高い。したがって OBS のプロセスだけを neko7 に置いても、neko5 で portal キャプチャを使う限りローカルの DS 制約は回避できない。GSR で物理モニターを指定する経路は compositor の portal を通らない構成が可能だが、実際の KMS plane、ドライバー、GSR のバージョン、権限、出力バッファの状態次第であり、DS 維持を保証するものではない。

GSR の `-w screen` は最初のモニターを選ぶ指定で、`-w eDP-1` 等は名前を持つ特定モニターを対象とする。`-w portal` は PipeWire/Portal に切り替える指定。したがって `screen` と `portal` は同義ではない。GSR によるキャプチャは osu! の OpenGL プロセスに `libobs_glcapture.so` を注入しないため、今回の EGL export クラッシュを回避する経路となる。ただし、GPU の Video engine、Render engine、メモリ帯域、消費電力への影響は残る。

映像を他ホストへ送るには、何らかのバッファ取得とデータ転送が必要になる。ここでいう「Direct」は、少なくとも (a) ゲームの scanout が compositor の再描画を省くこと、(b) キャプチャがゲームのフレーム待ちを増やさないこと、(c) 不要な CPU readback を避けること、(d) エンコードの実行場所を明確にすること、という複数の独立した条件として扱うべきである。完全にコピーや同期が存在しない配信を前提にしない。

根拠: [GSR マニュアル](https://man.archlinux.org/man/extra/gpu-screen-recorder/gpu-screen-recorder.1.en)、[Hyprland 画面共有](https://wiki.hypr.land/useful-utilities/screen-sharing/)、[Hyprland Direct Scanout 実装](https://github.com/hyprwm/Hyprland/blob/main/src/output/Monitor.cpp)。

## 10. SplitCast の実装されたデータフロー

SplitCast は単なる「neko7 で OBS を起動する仕組み」ではない。`packages/splitcast` に `capture` と `production` の2役があり、各ホストの Python agent が自分の子プロセス群を所有する。外側のサービス境界が systemd、内部は `idle / preparing / ready / running / degraded / failed / stopping` という Lifecycle と、strict schema の設定で管理する。

ゲーム経路の実装は `media.py::game_command()` に明記されている。`gpu-screen-recorder -w <capture.target> -s <width>x<height> -f <fps> -fm cfr -k h264 -encoder gpu -fallback-cpu-encoding no -tune performance -bm cbr -q <bitrate_kbps> -keyint 2 -a <game_audio> -ac aac -ab 192 -cursor no -c flv -o rtmp://127.0.0.1:<rtmp_port>/game` に相当する。既定の example では映像 1920×1080、60fps、12,000 kbps、ゲーム音声選択未設定で、設定を埋めない限り実キャプチャは始められない。

GSR の `-s 1920x1080` は出力解像度の上限であり、1366×768 の画面を必ず 1920×1080 に拡大する指定ではない。`-q 12000` は `-bm cbr` と組み合わせたとき kbps 単位のビットレート、`-keyint 2` は秒単位のキーフレーム間隔となる。また GSR のマニュアルでは `-tune performance` の効果は NVIDIA に限定され、`-fm cfr` は処理落ち時にエンコーダーへ負荷をかける場合があるとして推奨されていない。Intel iGPU でそれらの指定を「高速化済み」と扱わず、必要性と影響を測定する。これはローカルの neko5 で画面取得だけでなく H.264 エンコードも実行する設計だ。`-encoder gpu` と CPU fallback 禁止はソフトウェアエンコードへの暗黙の切り替えを拒否するが、Intel iGPU でどの GPU エンジンがどれだけ稼働しているか、実用フレームレートを維持できるかは実機測定が必要である。`neko7` への搬送は SSH の loopback forward と MediaMTX による RTMP、ゲームの受け取り後は OBS `ffmpeg_source` でのデコード、シーン合成、録画・Twitch 配信へ進む。したがって、最終出力でもエンコードする場合はエンコード段が2回になる。この再圧縮は画質・遅延・処理負荷に影響する。ソースと実装だけから必ず 2 回と断定するのではなく、実際の出力構成と encoder を観測する。

マイク経路はゲーム映像と独立する。neko5 で Pulse/PipeWire の生マイク音声を FFmpeg で 48 kHz mono／Opus 96 kbps として RTSP/TCP 送信し、neko7 でデコード後、RNNoise LADSPA、highpass 80 Hz、volume、limiter を適用して明示名を持つ Pulse sink に出す。OBS はその `.monitor` を取り込む。MicProcessed の同期は `mic_offset_ms`、カメラは `async_delay_filter` の `offset_ms` で補うが、固定オフセットだけでドリフトや再接続時の音声映像同期が保証されるわけではない。

カメラは H.264 native 転送または VAAPI/NVENC、VOICEVOX を使った TTS は遠隔合成とローカル再生、オーバーレイは OBS text source という別経路を持つ。認証にはローカルの秘密ファイルと bearer token、OBS WebSocket、SSH host key を使用する。RTMP/RTSP の media listener や OBS WebSocket は loopback へ閉じる設計で、秘密値を設定 JSON に直書きしない。アーキテクチャの書き直し時は、キャプチャ・音声・TTS・認証・ライフサイクルを無造作に混ぜず、境界ごとの不変条件として残す必要がある。

`config.py::ROUTES` には `game.av → capture.gpu → transport.rtmp → obs.game` 等の有限の route が固定されている。`agent.py::prepare()` では doctor、SSH tunnel、remote owner、MediaMTX、OBS を順に構築し、`start()` では senders、moving media、録画・配信の出力 bytes を検証する。`doctor()` は GSR 機能やターゲット選択、ゲーム音声選択を調べるが、Direct Scanout が維持されることまでは検査しない。`capture.target=portal` は DS と衝突し得る一方、`screen` や物理モニター名なら KMS キャプチャを検証できる。obs-vkcapture を使うゲームフック経路は現行 SplitCast には実装されていない。

GitHub の `neko5/configuration.nix` では SplitCast capture が NixOS/HM とも `enable = false` なのに対し、neko7 の production は有効である。HM の capture/prod user service は `WantedBy = []` で自動起動を前提としない。実機で現在何が稼働しているかは repository 上の boolean だけでは確定できない。

2026-11-01 の `TEST_RESULTS.md` では Python の45テストが全通過しているが、主に synthetic transport と CLI、HTTP、OBS/Pulse 接続、RNNoise、ready/lease cleanup、Firefox UI を検査したものである。実ゲームの GSR capture、Intel iGPU のフレーム時間比較、遠隔 SSH 越しの長時間配信、実 Twitch 送出、実 OBS NVENC の完走は未実施と明記される。テスト通過を Direct Scanout 維持の証明として使ってはならない。

根拠: [SplitCast README](https://github.com/tenzyu/nixfiles/blob/main/packages/splitcast/README.md)、[media.py](https://github.com/tenzyu/nixfiles/blob/main/packages/splitcast/splitcast/media.py)、[agent.py](https://github.com/tenzyu/nixfiles/blob/main/packages/splitcast/splitcast/agent.py)、[config.py](https://github.com/tenzyu/nixfiles/blob/main/packages/splitcast/splitcast/config.py)、[obs.py](https://github.com/tenzyu/nixfiles/blob/main/packages/splitcast/splitcast/obs.py)、[TEST_RESULTS.md](https://github.com/tenzyu/nixfiles/blob/main/packages/splitcast/TEST_RESULTS.md)。

## 11. NixOS／Home Manager の構成境界

この Nix リポジトリでは、`modules/50-features` が feature ごとに NixOS module と Home Manager module を提供し、`modules/00-hosts/neko5/configuration.nix` が `local.features` とユーザー側 `features` のスイッチを選択する。`osu-lazer.nix` は Nixpkgs のゲーム実行ファイルを探すラッパーと desktop entry を定義する。`osu-lazer-hyprland.nix` は `window_rule` を通じて compositor の扱いを指定する。`hyprland-tenzyu.nix` には `SDL_VIDEODRIVER=wayland`、`render.direct_scanout = 1`、Win+F の Lua dispatcher、VRR と描画設定がある。

以前の launcher には `hypr-gaming-mode on`、`trap 'hypr-gaming-mode off' EXIT`、`exec gamemoderun` の組み合わせがあった。一般に、シェルの `exec` はプロセスを置き換えるため、ゲーム終了時にそのシェルの EXIT trap が通常のシェル終了として走ることを前提にしてはいけない。mako を止め、waybar へ `SIGSTOP` を送る構成なら、復旧漏れは見た目と入力動作に影響する。`gaming-core.nix` の GameMode 設定や Gamescope の存在は Steam 向けにも必要であり、osu! の launcher を簡素化することと、全体のゲーム機能を削除することは別の設計判断である。

`mako.nix` の元設定は `layer = "overlay"`。統合パッチでは `top` への変更と osu! の強制 Fullscreen ルール削除などを提案したが、GitHub 上の main と実機の activated generation は一致保証がない。`git apply --check` は差分の適用可能性、`git diff --check` は空白等、`nh os build` は Nix のビルド、`nh os switch` は activation の確認である。これらは別々の検証であり、特に Direct Scanout と入力遅延の実機確認はビルドだけでは行えない。

`xdg-mime` の読み取り専用エラーも同じ構成管理の話である。実機では `~/.config/mimeapps.list` が `home-manager-files/.config/mimeapps.list` から `/nix/store/...-mimeapps.list` に解決され、`xdg-mime` が同じ読み取り専用ディレクトリへ `.new` を作ろうとして失敗した。`modules/50-features/dolphin.nix` には `xdg.mimeApps.enable = true` と `.osk` 用 `defaultApplications` の宣言がある。関連付けを変更する際には Home Manager を更新し、生成した Nix store のファイルを直接書き換えない。エラーを出した MIME 種別と呼び出し元は未確認であり、EGL の SIGSEGV の直接原因とは見なさない。

根拠: [neko5 host](https://github.com/tenzyu/nixfiles/blob/main/modules/00-hosts/neko5/configuration.nix)、[osu launcher](https://github.com/tenzyu/nixfiles/blob/main/modules/50-features/osu-lazer.nix)、[osu window rules](https://github.com/tenzyu/nixfiles/blob/main/modules/50-features/osu-lazer-hyprland.nix)、[Hyprland 設定](https://github.com/tenzyu/nixfiles/blob/main/modules/50-features/hyprland-tenzyu.nix)、[MIME 設定](https://github.com/tenzyu/nixfiles/blob/main/modules/50-features/dolphin.nix)。

## 12. 観測と性能検証の設計

「速い気がする」だけでは Direct Scanout、有効フレームレート、入力表示遅延、GPU エンコード負荷のどれが改善したか分離できない。まず変数を固定する。ゲームのバージョン、譜面、Mod、入力デバイス、フレームリミッター、VSync、osu! の表示モード、Hyprland、CPU governor、電源・温度、録画方式、GSR encoder flags、OBS profile を保存する。比較の単位は `game_only`、`obs_current`、`splitcast` とし、それぞれ複数回計測する。

計測では平均 FPS だけでなくフレーム時間の p50/p95/p99、long frame 数、CPU one-core usage、Intel GPU の Render/3D engine と Video engine、VRAM/共有メモリ、温度・クロック・電力、システムのドロップフレーム、音声ドリフト、Tailscale の direct/relay と RTT を追う。フレーム時間 16.67 ms は 60 FPS、8.33 ms は 120 FPS に対応する計算値であって、このマシンでの測定結果ではない。総入力遅延はペン入力のタイムスタンプから実ディスプレイの発光まで測らない限り、ゲーム内フレーム時間だけでは分からない。

提供された `scripts/splitcast/perf.py` は `game_only`／`obs_current`／`splitcast` の比較と外部フレーム CSV、`intel_gpu_top -J` の Render/Video engine、Tailscale status 等の取得を設計している。既存の収集基盤を活用し、表示経路には `hyprctl monitors -j` の DS 状態を合わせて保存する。収集方法がゲームの fullscreen 状態を変えてしまわないよう、定期取得は別プロセスで行い、端末に切り替えてフォーカスを失った状態をゲーム中のデータと混同しない。

性能改善の合格条件は単一の FPS 数字にすべきではない。最低限、「ゲームがクラッシュしない」「ゲーム入力の座標が変わらない」「必要な場面で Direct Scanout が成立する」「p99 のフレーム時間や入力表示遅延が、ゲームのみの基準からどれだけ増えるかが測定されている」「映像・音声の品質と同期が許容範囲に収まる」を別々に判定する。閾値は実測前に仮の値を検証済みと称して固定せず、比較結果とユーザーの許容値から決める。

## 13. SplitCast 書き直し前の ADR 論点

ADR は「ライブラリを何に変えるか」より先に、「どの契約を守るか」を固定すると価値がある。今回の必須条件は、ゲームの OpenGL/native Wayland を維持すること、入力の1280×720設定と実際のタブレットマッピングを保持すること、Direct Scanout の成立条件を後退させないこと、キャプチャ不能時もゲームをクラッシュさせないこと、ローカルの通常プレイをネットワークや neko7 の状態から独立させること、音声をローカルで聴けること、秘密情報を守ること、失敗後にすべての子プロセスとリソースを回収できること、追加支出を発生させないことだ。

意思決定の対象は、(a) キャプチャ境界を `GL swap`、`DRM/KMS`、`PipeWire portal` のどれに置くか、(b) `neko5` で行う最低限の処理は画面取得までか H.264 encode までか、(c) 専用 OBS へ渡すプロトコルと動画フォーマット、(d) audio/video の時刻同期と再接続、(e) DS を実際の実行時条件として監視する方法、(f) 失敗時の rollback と production の責務の境界、となる。

比較で重要なのは、GSR の DRM/KMS は既にアプリケーション内にあるため、まず実機で DS と性能の影響を調べる価値があること。obs-vkcapture の GL hook は画面共有 portal を避ける利点がある一方、現在は実機で再現性の高い SIGSEGV があるため、採用するなら crash isolation、EGL 初期化の修正、GL-only 保証、回帰テストを先に満たす必要があること。PipeWire portal は一般的な互換性が高いが、Hyprland の Direct Scanout と原理上衝突し得ることだ。

ADR は実装パッチではない。決定の根拠として、再現ログ、ソース参照、実機性能の比較、採用／不採用の理由、失敗条件、rollback、残存リスクを残す。完成後に初めてドメインモデル、処理境界、設定スキーマ、テスト、移行計画を変更する。既に SplitCast に存在する child ownership、lease、認証、独立音声処理、OBS sink 監視、retry 上限は、書き直しの際に失われやすいので明示的な不変条件として継承すべきである。

## 14. 現時点で確定していない事実

現行の activated `neko5` がどの NixOS generation、Hyprland の正確なバージョン、Mesa/GLVND、osu! の起動ラッパーを使用しているか。`Win+F` 後の client/internal 状態と実際の `wl_buffer` pixel size。静的 `fullscreen_state = "2 0"` だけで起動時から同じ状態を再現できるか。OBS の EGL dispatch で渡された display handle と vendor dispatch の整合性。GSR の KMS capture がこの Intel iGPU と特定の Hyprland 世代で DS を保つか。SplitCast が実機で capture agent を起動しているか、動画/音声の長時間同期、neko7 NVENC 出力、Tailscale が direct/relay のどちらなのか。これらは資料だけでは確定できない。

この未確定事項を、過去に提示したパッチの存在や upstream ソースの仕様から自動的に「実施済み」「解決済み」に変えないことが、今後の設計とデバッグの前提になる。また upstream の `main`／`master` と、稼働中の `osu-lazer-bin-2026.1005.0` や NixOS に含まれる Hyprland/SDL3/Mesa のコードは版が異なる可能性がある。故障を特定する段階では Nix store の derivation と実行バイナリに対応するソースへ絞って再照合する。

## 15. 非破壊の実行時観測コマンド

以下は設定を変更せずに動作状況を記録する例である。`hyprctl clients` の `fullscreen` は compositor 内部のモード、`fullscreenClient` はアプリへ伝えたモードなので、同じ Fullscreen という言葉でも値が異なり得る。

```bash
# osu! を前面に出した状態で、別ターミナルや事前起動の採取処理から実行
hyprctl clients -j | jq '[.[] | select(.class == "osu!" or .class == "osu-lazer") | {class, initialClass, xwayland, fullscreen, fullscreenClient, size, monitor}]'

# DS の実動作と阻害理由（有無だけではなく directScanoutTo も確認）
hyprctl monitors -j | jq '[.[] | {name, width, height, scale, directScanoutTo, directScanoutBlockedBy, solitaryBlockedBy, activelyTearing}]'

# GSR の使用可能な対象とエンコーダーの検出（録画を開始しない）
gpu-screen-recorder --list-capture-options
gpu-screen-recorder --info

# OTD Daemon が停止しているか。ゲーム内蔵 OTD の動作はゲームの UI とログで別に確認
systemctl --user is-active opentabletdriver.service || true
pgrep -af 'otd-daemon' || true
```

キャプチャ開始時の DS 状態を調べる場合、ターミナルへのフォーカス切り替えでゲームの Fullscreen/solitary 判定が変わる可能性がある。観測コマンドをゲーム起動前にバックグラウンド起動しておく。

```bash
mkdir -p /tmp/osu-diagnostics
(
  for i in $(seq 1 60); do
    hyprctl monitors -j | jq -c --arg ts "$(date -Is)"       '[.[] | {ts: $ts, name, directScanoutTo, directScanoutBlockedBy, solitaryBlockedBy, activelyTearing}]'
    sleep 1
  done
) > /tmp/osu-diagnostics/scanout.jsonl 2> /tmp/osu-diagnostics/errors.log &
# ゲームに戻る。この1秒周期の観測は DS の状態を追うためのもので、精密な遅延計測ではない。
```

OBS の SIGSEGV の確認に必要な最小情報は次のように取得できる。全環境変数の出力は秘密値を含み得るため避ける。

```bash
coredumpctl --no-pager info 7099 | sed -n '1,110p'
# ゲームを OBS source 取得前に起動した状態で実行
pid=$(pgrep -n -x 'osu!')
awk '/lib(EGL|GLdispatch|obs_glcapture|gallium)/ {print $6}' "/proc/$pid/maps" | sort -u
tr '\0' '\n' < "/proc/$pid/environ" | grep -E '^(LD_LIBRARY_PATH|LD_PRELOAD|EGL_PLATFORM|MESA_LOADER_DRIVER_OVERRIDE)=' || true
```

このログは「どの共有ライブラリをロードしていたか」を調べるだけである。原因を確定するには GDB のクラッシュスレッド、EGLDisplay の実体、EGL extension の動作、ソースに対応したデバッグ情報が別途必要となる。
